01 — Mechanism

What happens between SubmitOrder and the response

A gRPC handler thread never touches the book directly. It hands the order to a lock-free queue and blocks on a promise — the reply comes back through that promise, not back through the queue. Fills fan out to every subscriber on a completely separate path.

Queue topology
buffer-list, 1620/segment

Producers race a CAS to extend the linked list of fixed buffers; the single consumer scans ahead and folds fully-drained segments back into a garbage list for reuse.

Consumer loop
busy-spin, no sleep

The matching thread is the only thing standing between an enqueue() and a blocked client — it costs one core at ~100%, spent deliberately on latency instead of CPU headroom.

Book structure
std::map<price, std::list<Order>>

Bids sorted high→low, asks low→high; std::list specifically so a cancel elsewhere never invalidates the iterator an order's id maps to.

Fan-out
1 queue per subscriber

Every Subscribe stream gets its own MPSCQueue<MarketEvent> — the same primitive that feeds the matching engine, reused because the topology is trivially single-producer.

02 — Price-time priority

Whoever quotes first, fills first

Each price level is a FIFO list. An incoming order walks the opposite book from the best price outward, consuming resting orders oldest-first at every level it crosses — partial fills keep their place in line rather than losing priority.

A LIMIT that doesn't fully cross rests at its price. A MARKET order that can't fully fill is rejected outright — quantity that did execute still gets reported, but nothing is left resting.

03 — One binary, five personalities

The bots that keep the book honest

node.exe --strategy=<name> is the only client program — every strategy below is a flag, sharing one gRPC client and one Subscribe listener. A PowerShell launcher starts ten of them at once against the same book.

market-maker

Quotes both sides, always

Rests a bid and an ask around the current mid, re-quoting whenever price drifts past a threshold. The default source of resting liquidity everyone else trades against.

--mm-spread--mm-size--mm-requote-threshold-pct
momentum

Chases the last N trades

Tracks a rolling trade-price window; a market order fires in the direction of the recent trend once it clears a threshold return.

--mom-window--mom-threshold-pct
mean-reversion

Bets against the drift

Same rolling window, opposite conviction — a limit order fades price once it strays too far from its own moving average.

--mr-window--mr-deviation-pct
noise

Randomized activity generator

Random side, size and price jitter on a probability gate each tick, with a standing chance to cancel its own resting orders. Pure liquidity noise — the busiest bot in the room.

--noise-action-prob--noise-cancel-prob
replay

Drives the book on a script

Loads a bundled CSV of (offset, price) checkpoints and nudges the market toward each one on an accelerated clock — a deterministic scenario, not a reaction to it.

--replay-file--replay-speed--replay-loop

Method. Windows 11, MSYS2 UCRT64 g++ 15.2, exchange and benchmark client both on localhost, insecure gRPC channel, one order per RPC, Release-equivalent build (no sanitizers). Sequential = a single client issuing one blocking SubmitOrder call at a time after a 200-call warmup. Concurrent = 8 client threads, 1,500 calls each, wall-clock across the whole run. MPSC numbers are the queue in isolation — no gRPC, no matching logic, just enqueue/dequeue. The p99-to-max gap (0.33ms → 2.0ms) is one real scheduler/allocator blip in a few thousand calls, not a rounding artifact — shown rather than hidden.
